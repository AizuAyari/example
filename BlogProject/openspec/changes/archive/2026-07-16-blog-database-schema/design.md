## Context

現在 `blog/models.py` は空で、データモデルが一つも定義されていない。「The Blogs」はユーザー登録・記事投稿・閲覧・検索・フィルタリングを提供するブログプラットフォームであり、これらの機能の土台となるデータベーススキーマを確立する必要がある。

要件（システム仕様より）:
1. `users`: Django 組み込み `User` モデル（一意なユーザー名・ハッシュ化パスワード）
2. `articles`: `title`, `content`, `author`（`User` への外部キー、`on_delete=CASCADE`）, `created_at`（`auto_now_add=True`）, `updated_at`（`auto_now=True`）
3. `keywords`（Phase 2・オプション）: `keyword_text`, `article`（`Article` への外部キー）

制約（CLAUDE.md より）:
- ユーザー登録・パスワードハッシュ化には Django 組み込み `User` モデルを使用する
- 記事は著者情報と投稿日時を持つ
- 記事一覧はデフォルトで新しい順（降順）に表示する
- 全モデルに管理画面で識別しやすい `__str__()` を実装する
- 既存マイグレーションは編集せず、新規マイグレーションを作成する
- 小さく的を絞った変更を優先する

## Goals / Non-Goals

**Goals:**
- `Article` モデルと（Phase 2 用の）`Keyword` モデルを `blog/models.py` に定義する
- Django 組み込み `User` モデルをそのまま外部キー参照先として使用する（カスタムユーザーモデルへの置き換えは行わない）
- `blog/admin.py` に `Article`・`Keyword` を登録し、管理画面から確認・編集できるようにする
- 初期マイグレーションを生成し、`created_at`/`updated_at` を自動管理させる
- 記事のデフォルト並び順を新しい順（`-created_at`）にする

**Non-Goals:**
- カスタムユーザーモデル（`AUTH_USER_MODEL` の変更）は行わない
- 認証ビュー・登録フォーム・検索/フィルタリング UI の実装は本変更のスコープ外（別変更で扱う）
- `Keyword` のタグ付け UI・多対多関連の高度な設計（例: 正規化された `ManyToMany` 経由のタグ一覧画面）は Phase 2 の別変更で扱う。本変更では最小限の外部キー構造のみ定義する

## Decisions

### 1. `User` は Django 組み込みモデルをそのまま使用する

`django.contrib.auth.models.User` を変更・拡張せずに直接参照する。`AUTH_USER_MODEL` の設定変更は行わない。

**理由**: CLAUDE.md およびシステム仕様が明示的に「Django 組み込み User モデル」を要求している。組み込みモデルは一意な `username` 制約とパスワードハッシュ化（PBKDF2 等）を標準で提供するため、追加実装が不要。

**代替案として検討**: `AbstractUser` を継承したカスタム `User` モデル → 将来的な拡張性（例: プロフィール項目追加）はあるが、要件外であり、既存プロジェクトで一度 `migrate` 後に `AUTH_USER_MODEL` を変更するのは実質不可能に近い（DB 再構築が必要）。要件を満たすシンプルさを優先し不採用。

### 2. `Article.author` は `on_delete=models.CASCADE`

著者ユーザーが削除された場合、その著者の記事も連鎖的に削除する。

**理由**: 要件で明示的に指定されている。ブログ記事は著者に強く紐づくコンテンツであり、孤立した記事を残さない方が一貫性がある。

**代替案として検討**: `SET_NULL`（著者情報を匿名化して記事を残す）→ 要件外のため不採用。将来的に必要になれば別変更で `null=True` 化を検討する。

### 3. `Article` のデフォルト並び順は `Meta.ordering = ["-created_at"]`

モデルレベルで `Meta.ordering` を設定し、明示的な `order_by()` なしでも新しい順に取得されるようにする。

**理由**: CLAUDE.md の「記事は降順（新しい順）で表示する」という規約をモデル層で保証し、ビュー実装時の指定漏れによるバグを防ぐ。

### 4. `Keyword` は `Article` への `ForeignKey`（多対多ではなく一対多）

要件の記述（`article_id` を外部キーとして持つ）に従い、1つの `Keyword` レコードは1つの記事に属する構造とする（同じキーワード文字列が複数記事に紐づく場合は行が重複する）。

**理由**: 要件の table 定義に忠実に従う。Phase 2 はオプション扱いであり、正規化（`ManyToMany` + 独立した `Keyword` マスタ）は将来の改善余地として Open Questions に記載し、今回はスコープを広げない。

**代替案として検討**: `ManyToManyField` によるタグ正規化 → 検索効率や重複排除の観点で優れるが、要件に明記された `article_id` 外部キー構造と異なり、スコープ拡大になるため不採用。

### 5. `__str__()` の実装

- `Article.__str__()` → タイトルを返す（管理画面で記事を識別しやすくする）
- `Keyword.__str__()` → キーワードテキストを返す

**理由**: CLAUDE.md の規約（全モデルに読みやすい `__str__()` を実装）に従う。

## Risks / Trade-offs

- [`Article.author` の `CASCADE` によりユーザー削除時に記事が消える] → 将来的に「退会ユーザーの記事は匿名化して残す」要件が出た場合はスキーマ変更（`SET_NULL` + `null=True`）と新規マイグレーションが必要になる。現時点では要件通り `CASCADE` を採用し、リスクとして記録するに留める。
- [`Keyword` を一対多構造にしたことで同一キーワード文字列が記事ごとに重複行として存在する] → キーワード横断の集計・検索を行う場合はクエリが冗長になる。Phase 2 で本格的なタグ機能を実装する際に `ManyToMany` への移行を再検討する。
- [Django 組み込み `User` モデルはメールアドレスの一意性を強制しない] → 現状の要件はユーザー名の一意性のみを求めているため対応不要だが、将来メール認証やパスワードリセットを追加する場合は別途検討が必要。

## Migration Plan

1. `blog/models.py` に `Article` モデルを追加する
2. `blog/models.py` に `Keyword` モデルを追加する（Phase 2、`Article` 定義後に配置し `ForeignKey` 参照を解決する）
3. `python manage.py makemigrations blog` で初期マイグレーションを生成する
4. 生成されたマイグレーションファイルの内容を確認する（フィールド定義・`on_delete` 挙動）
5. `python manage.py migrate` をローカル/開発 DB に適用する
6. `blog/admin.py` に `Article`・`Keyword` を登録する
7. `pytest` でモデル関連のテストを実行し、既存テストの回帰がないことを確認する

**ロールバック**: 本変更は新規モデル追加のみで既存テーブルへの変更を伴わないため、問題があれば当該マイグレーションを `migrate blog <前のマイグレーション名>` で戻すか、マイグレーションファイルと `models.py` の追記分を取り消すことで対応可能。

## Open Questions

- `Keyword` を Phase 1 で実装するか、Phase 2 として本当に見送るか（要件では "Optional" 明記のため、本変更では `Article` と合わせてモデル定義自体は作成するが、関連ビュー・検索機能は別変更に委ねる想定）
- 将来的に `Keyword` を `ManyToMany` ベースの正規化構造へ移行する必要があるかは、実際のタグ検索・フィルタリング要件が固まった時点で再検討する
